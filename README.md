# Modul 10 Asynchronous Programming

## Experiment 1.1: Original timer from the book

Implementasi awal dari buku Rust Async Chapter 2.3. Kode mengimplementasikan Custom Executor, Spawner, TimerFuture, dan pergerakan asinkron untuk mencetak pesan dengan interval 2 detik menggunakan *background thread* dan mekanisme `Waker`.

## Experiment 1.2: Understanding how it works

Sebagai koreksi teknis yang fundamental, urutan eksekusi terminal yang sebenarnya akan terjadi adalah tercetaknya pesan "Fide's Komputer: hey hey" terlebih dahulu, baru kemudian diikuti oleh pesan "howdy!" dan "done!". Hal ini terjadi karena pemanggilan fungsi `spawner.spawn` pada dasarnya tidak langsung menjalankan blok *async* ataupun memanggil metode `poll` pada objek *future* tersebut. Fungsi instruksi `spawn` ini sekadar bertugas membungkus *future* tersebut ke dalam struktur memori `Task` dan mengirimkannya (mengantrekannya) ke dalam antrean *channel* MPSC. Karena tidak ada eksekusi yang tertunda atau memblokir, *main thread* program akan langsung melangkah memproses baris sintaks berikutnya, mencetak output "Fide's Komputer: hey hey" secara instan. Baru setelah fungsi `executor.run()` dipanggil di baris terbawah program, *executor* akan mulai bertugas mengambil entri *task* dari dalam sisi *receiver channel* dan menjalankan operasi *polling* pertamanya terhadap state. Tepat pada proses *poll* pertama inilah isi dari blok instruksi `async` dieksekusi maju, yang menyebabkan "howdy!" tercetak di layar, sebelum akhirnya eksekusi tersuspensi atau tertahan (mengembalikan flag `Poll::Pending`) ketika mencapai titik `.await` pada `TimerFuture`. Begitu durasi dua detik pada *thread* latar belakang *timer* selesai terpenuhi, metode `wake()` akan dipanggil guna mentransfer *task* tersebut kembali ke dalam *channel*, di mana akhirnya `executor` dapat melakukan siklus *poll* yang kedua untuk menuntaskan rutinitas program dan mencetak pesan pamungkas "done!".

## Experiment 1.3: Multiple Spawn and removing drop

Penerapan *multiple spawn* secara berulang akan mengakibatkan ketiga *task* asinkron tersebut didorong ke dalam *channel* eksekutor untuk segera diproses secara paralel dan saling bergantian (konkuren). Akibatnya, pada *output* urutan di konsol, seluruh instruksi pencetakan tulisan (seperti "howdy!", "howdy2!", dan "howdy3!") akan dicetak secara berurutan seketika pada saat operasi *polling* fase pertama memproses tiap tugas tanpa terblokir. Secara bersamaan, durasi total eksekusi program tidak melipatgandakan diri secara linier menjadi sekitar 6 detik, melainkan tetap akan merampungkan eksekusinya pada kurun waktu kurang lebih 2 detik saja sebab ketiga siklus penungguan simulasi *timer* latar belakang berjalan secara tumpang tindih (*overlapping*).

Dalam model arsitektur pemrograman *async* berbasis perpesanan ini, instrumen `Spawner` memposisikan dirinya khusus sebagai gerbang pengirim (*Sender* di arsitektur `mpsc`) yang berkewajiban semata-mata menyelipkan objek `Task` anyar ke ujung lorong antrean penyelesaian tanpa mengeksekusinya. Berlawanan dengannya, `Executor` mengambil lakon mutlak sebagai agen penerima muatan (*Receiver*) yang bersiklus secara repetitif guna mengangkut kumpulan antrean pesan tadi untuk selanjutnya mengevaluasi state kemajuan *future* (melakukan `poll`). Hubungan antar keduanya dirangkai sangat erat oleh entitas perantara bernama `Waker`, yang mana tatkala sebuah *future* yang tertidur menyadari dirinya sudah siap melangkah, `Waker` bertindak menduplikasi diri guna mensirkulasikan kembali *Task* tersebut agar mendarat di *channel* `Spawner` dan dijemput ulang oleh `Executor`.

Jika kita melakukan penghapusan atau meletakkan komentar pada instruksi `drop(spawner)`, maka eksekusi program utamanya akan gagal mencapai garis akhir dan malah terjebak di dalam siklus *infinite loop* (proses berdiam atau *hang*) mutlak di ranah `executor.run()`. Anomali tersebut terwujud dikarenakan mekanisme metode ekstraksi `recv()` di dalam arsitektur siklus iterasi *executor* berstatus konstan dalam memblokir atau menahan jalan program sembari mengharap kedatangan instruksi lanjutan. Oleh sebab variabel instans `spawner` tidak dihancurkan secara eksplisit, koneksi antar perantara saluran MPSC terus mendeteksi bahwa masih ada setidaknya sisa satu simpul referensi pengirim (*Sender*) yang aktif. Alhasil, fungsi penerima tidak akan memancarkan interupsi *Error* penutupan kanal dan `Executor` akan rela tidur tertahan tanpa durasi batas (*infinity*) guna mengantisipasi pesan kiriman tambahan yang pada faktanya takkan pernah diformulasikan lagi oleh *thread* utama.

## Experiment 2.1: Original code, and how it run

Untuk menjalankan aplikasi ruang obrolan secara bersamaan, Anda dituntut untuk membuka beberapa *instance* terminal sekaligus. Pada terminal pertama, jalankan perintah `cargo run --bin server` untuk memulai peladen utama yang bertugas mendengarkan koneksi masuk. Kemudian, pada sisa terminal lainnya, Anda dapat menjalankan perintah `cargo run --bin client` untuk menyambungkan klien-klien yang baru ke jaringan server tersebut. Di balik arsitekturnya, penggunaan modul *channel* `tokio::sync::broadcast` memungkinkan sistem peladen untuk mengelola *state* fanning yang kompleks dari berbagai koneksi *websocket* tanpa perlu melakukan prosedur *lock* manual. Ketika terdapat satu klien yang memutuskan untuk mengirimkan baris pesan teks, server akan membaca pesan masuk tersebut dan otomatis mempublikasikannya melalui *endpoint sender* menggunakan metode `bcast_tx.send(text)`. Berkat kehebatan *broadcast*, pesan tersebut kemudian akan langsung disebarluaskan (di-*fan-out*) ke seluruh kloningan *receiver* yang terhubung dengan sirkuit *channel* yang sama. Setiap *task* peladen koneksi yang sedang beroperasi asinkron di dalam *thread pool* akan langsung terbangun, mengurai pesan teks dari dalam *channel*, dan meneruskannya kembali ke masing-masing klien melalui jembatan jaringan koneksi *websocket* mereka.

## Experiment 2.2: Modifying port

Untuk merealisasikan perubahan *port* lalu lintas aplikasi *websocket* ini, terdapat dua buah lokus komponen yang wajib dimodifikasi secara seirama agar negosiasi koneksi dapat sukses terjalin. Pada level program peladen (`server.rs`), kita terikat keharusan untuk memperbarui nilai target alamat *binding* pada instruksi `TcpListener::bind` agar sistem operasi membuka dan memantau *port* 8080. Sementara bergeser di level klien (`client.rs`), alamat tujuan URI pada metode statis `Uri::from_static` juga dituntut untuk diubah presisi menjadi pola `"ws://127.0.0.1:8080"`. Alasan fundamental mengapa penyesuaian kedua sisi ini harus diselaraskan secara absolut adalah karena model arsitektur komunikasi *client-server* tradisional mengamanatkan kehadiran sebuah titik pertemuan spesifik (*endpoint port*) yang disepakati oleh *listener* dan pengirim *handshake*. Secara lebih dalam, spesifikasi pertukaran data dari protokol WebSocket (`ws://`) pada praktiknya selalu mengeksploitasi keandalan sambungan TCP sebagai lapisan transportasinya. Sebelum komunikasi tersebut dielevasi (di-`upgrade`) menjadi pipa perpesanan *full-duplex* via WebSocket, *library* milik klien diwajibkan melakukan ritual negosiasi HTTP dasar (*handshake*) dengan melintasi *port* TCP 8080 yang telah direservasi oleh server.

## Experiment 2.3: Small changes, add IP and Port

Untuk menambatkan identitas pengirim di sekeliling setiap pesan teks yang masuk, saya mengeksploitasi kombinasi atribut IP dan *Port* klien yang secara transparan direpresentasikan oleh entitas `SocketAddr`. Data soket *peer* tersebut diekstraksi tanpa sengaja sebagai hasil kembalian sekunder dari pemanggilan `listener.accept()`, yang cara kerja utilitasnya ekuivalen penuh dengan operasi manual pemanggilan `peer_addr()` pada *stream* TCP reguler. Seusai diekstraksi, komponen `addr` ini dilimpahkan langsung ke dalam pusaran fungsi asinkron *handler* agar direferensikan pada iterasi *event loop*. Saat sebuah perpesanan klien tertangkap oleh server dan sebelum dilepaskan kembali ke arus utama *channel broadcast*, saya merakit untaian string menggunakan bantuan sintaks khusus makro `format!`. Sintaks konstruktif inilah yang mencangkokkan label alamat asli (contoh: `127.0.0.1:49838`) di bagian terdepan untaian teks pesan agar menjelma ke format string paripurna `"{ip}:{port}: {message}"`. Formulasi final beridentitas inilah yang disuntikkan secara dinamis ke eksekusi parameter `bcast_tx.send()` untuk diudarakan serentak. Tindakan memfasilitasi injeksi penanda koneksi bawaan pada data sebetulnya memegang urgensitas yang sangat masif ketika mengkonstruksi layanan obrolan *multiplex*. Di tengah ketiadaan subsistem keamanan statis pengenal pengguna (seperti *Session ID* atau pelacak token kriptografis JWT), elemen IP beserta angka spesifik *port* sumber bertransformasi menjadi satu-satunya *identifier* otonom yang bisa dimanfaatkan peladen guna melakukan diskriminasi entitas antar ribuan pengguna terdaftar.

## Experiment 3.1: Original code

Untuk memungkinkan bahasa Rust berjalan di dalam ekosistem peramban (*browser*), *framework* Yew memanfaatkan teknologi WebAssembly (WASM) yang secara ajaib mengkompilasi kode Rust menjadi set instruksi *low-level* yang sangat efisien. Melalui pemanggilan rutin `yew::prelude::*`, kita mendapatkan akses absolut ke berbagai utilitas esensial untuk mendirikan struktur UI yang secara murni berbasis komponen (*Component-Based UI*). Salah satu fondasi utamanya adalah *hook* reaktif `use_state` yang berperan sangat sentral dalam merekam sekaligus bereaksi terhadap setiap perubahan data (*lifecycle*), seperti riwayat pesan obrolan atau *input* dari pengguna. Setiap mutasi atau perubahan pada *state* ini akan memicu mesin *render* Yew untuk melukis ulang komponen secara otomatis sehingga visualisasi UI selalu teraktualisasi. Sementara itu, untuk menangani efek samping (*side effects*) fungsional seperti membuka dan menjaga koneksi sirkuit WebSocket, kita wajib memanfaatkan *hook* `use_effect_with`. Di dalam zona *hook* inilah siklus penerimaan pesan dari peladen terjadi secara asinkron tanpa henti di latar belakang, merayap dan membaca aliran *bytes* hingga memicu pembaruan status antarmuka ketika data baru mendarat.

## Bonus: Rust Websocket server for YewChat!

Untuk menjembatani perbedaan bahasa komunikasi fungsional antara klien terminal (yang berbasis aliran *plain text*) dengan klien web Yew (yang merujuk murni pada format JSON), saya telah merestrukturisasi metode *handler* di dalam `src/bin/server.rs` agar sanggup bertindak lebih fleksibel. Modifikasi fundamental ini diterapkan dengan cara memaksa peladen untuk terlebih dahulu mencoba melakukan proses *deserialization* (mengurai teks menjadi objek) terhadap pesan yang masuk menggunakan fungsi `serde_json::from_str`. Apabila pesan tersebut sukses terurai sebagai struktur `ChatMessage` (berarti mutlak datang dari klien Yew), maka server akan menyelipkan kombinasi metadata IP dan *Port* (*peer address*) langsung ke dalam parameter `username` sebelum menserialisasikannya kembali ke wujud JSON dan mem-*broadcast*-nya. Namun jika proses tersebut gagal (yang berarti pesannya hanyalah *string* teks primitif dari klien terminal), peladen akan secara elegan mengambil jalur *fallback* (*else branch*) untuk langsung menggabungkan alamat TCP dan teks ke dalam satu string tunggal (*plain string*). 

Secara subjektif, berbicara mengenai arah arsitektur pemilihan fondasi peladen masa depan, saya pribadi jauh lebih menaruh kepercayaan penuh untuk mengandalkan kapabilitas *backend* Rust yang ditenagai oleh mesin asinkronisasi `tokio` dibandingkan dengan *backend* Node.js / JavaScript murni. Dominasi Rust terasa sangat luar biasa absolut dalam aspek performa skalabilitas puncak (berkat toleransi *overhead* memori yang sangat rendah) serta tersedianya garansi keamanan struktural (*memory safety* tanpa *Garbage Collector*). Hal ini bersinar terang saat harus beroperasi mengelola memori dari puluhan ribu koneksi *websocket* secara konkuren (tanpa bayang-bayang *data races*), sebuah beban berat yang teramat sulit serta sangat rawan *runtime error* apabila diimplementasikan menggunakan sistem eksekusi monolitik berbasis *Single-threaded Event Loop* milik arsitektur bawaan JavaScript.
